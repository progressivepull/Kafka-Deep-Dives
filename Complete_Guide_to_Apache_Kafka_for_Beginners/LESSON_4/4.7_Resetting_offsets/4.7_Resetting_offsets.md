# 4.7 Resetting offsets

This lecture demonstrates how to reset committed consumer-group offsets using the Kafka Consumer Groups CLI or the Conduktor interface. A consumer group commits offsets so its consumers can resume reading from their previously committed positions. Resetting those offsets changes where the group will resume consuming retained records.

## Key concepts

- **Committed offset:** The saved position from which a consumer group resumes reading.
- **Consumer lag:** Records remaining between the group's committed position and the end of a partition.
- **Offset reset:** Changes the group's committed positions so records can be replayed or skipped.
- **`--to-earliest`:** Resets to the earliest currently available offset in each selected partition (often zero in a new topic, but not always).
- **`--dry-run`:** Previews the proposed offsets without applying changes.
- **`--execute`:** Applies the reset.
- **Inactive group:** Stop all consumers in the group before resetting offsets.

## Demonstration workflow

1. Describe the existing group `my-first-application` and inspect its lag. The lecture initially observes lag values of **2, 2, and 1**, totaling **5** messages.
2. Stop all consumers belonging to that group.
3. Preview an offset reset to the earliest available offsets for `third_topic`.
4. Execute the reset after checking the preview. In the lecture's example, the proposed offsets are **0, 0, and 0**.
5. Describe the group again; lag increases because the committed offsets now point further back.
6. Restart a console consumer using the same group ID. It re-reads the retained messages from the reset positions.
7. Inspect the group again after consumption and commits; the demonstrated lag returns to zero.

## Kafka CLI commands

### 1. Describe a consumer group

```bash
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group my-first-application
```

### 2. Preview resetting offsets to the beginning

```bash
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group my-first-application \
  --topic third_topic \
  --reset-offsets \
  --to-earliest \
  --dry-run
```

### 3. Execute the offset reset

**Important:** Make sure all consumers in the group are stopped and verify the topic and group before executing.

```bash
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group my-first-application \
  --topic third_topic \
  --reset-offsets \
  --to-earliest \
  --execute
```

### 4. Restart a consumer in the reset group

```bash
kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic third_topic \
  --group my-first-application
```

No `--from-beginning` flag is needed here: the group's saved offsets were already reset.

### 5. Verify progress and lag

```bash
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group my-first-application
```

## Other reset strategies mentioned in the lecture

| Strategy | Purpose |
|---|---|
| `--to-earliest` | Resume at the earliest available records. |
| `--to-latest` | Move to the end of the topic, skipping currently retained earlier records for that group. |
| `--to-offset` | Choose a particular offset. |
| `--to-datetime` | Reset based on a timestamp. |
| `--to-current` | Use the currently committed offsets. |
| `--shift-by` | Move offsets forward or backward by a relative amount. |

The lecture mentions these additional options without demonstrating each one.

## Resetting offsets in Conduktor

The instructor also demonstrates resetting offsets through the Conduktor UI. Select the consumer group, topic, partitions, and reset strategy, then apply the reset while the group is inactive. The UI can make it easier to inspect and choose the intended positions.

## Important cautions

- **Stop every active consumer in the group** before attempting the reset.
- **Always preview with `--dry-run`** and double-check the target group, topic, and partitions.
- Resetting to the earliest position replays only **records still retained** in Kafka; deleted or expired records cannot be recovered through an offset reset.
- A reset changes **consumer-group positions**, not the topic's messages themselves.
- On a secured cluster, the CLI may also need connection configuration such as `--command-config playground.config`, as introduced in earlier lessons.
- Depending on how consumers commit offsets, the observed lag may not become zero immediately after records appear in the console.

## Key takeaway

**Resetting consumer-group offsets controls where an existing group resumes reading.** Preview the change, stop the group's consumers, execute the reset, and restart consumers to replay retained records or resume at another chosen position.

## Key concepts
1. Committed offsets: Track where a Kafka consumer group should resume reading.
2. Resetting offsets: Changes the position from which consumers read messages.
3. --to-earliest: Resets offsets to the earliest available messages.
4. --dry-run: Previews the reset without modifying offsets.
5. --execute: Applies the offset reset.
6. Consumer lag: Can increase after resetting offsets backward.
7. Inactive consumers: All consumers in the group must be stopped before resetting offsets.
8. Conduktor UI: Provides a graphical alternative for resetting offsets.

# 2.9 Kafka KRaft- Removing ZooKeeper


## Overview
This lecture explains **Kafka KRaft mode**, the architecture that removes Apache ZooKeeper as a dependency for Kafka clusters.

## Background
- In **2020**, the Kafka project began work on eliminating the ZooKeeper dependency under **KIP-500**.
- Motivation: ZooKeeper limited scalability. Clusters struggled beyond ~100,000 partitions.
- With KRaft, Kafka can scale to **millions of partitions**.

## Benefits of Removing ZooKeeper
- Easier to maintain and set up
- Improved stability
- Simpler monitoring, support, and administration
- **Single security model** (only Kafka security, no separate ZooKeeper security)
- Single process to start
- Faster controller shutdown and recovery times

## Availability
| Version       | Status                          |
|---------------|---------------------------------|
| Kafka 3.x     | KRaft implemented               |
| Kafka 3.3.1+  | Production-ready (KIP-833)      |
| Kafka 4.0     | ZooKeeper support fully removed |

## Architecture Comparison
**With ZooKeeper:**
- Separate ZooKeeper quorum (with its own leader) manages Kafka brokers.

**With KRaft (Quorum Controller):**
- Only Kafka brokers exist.
- One broker acts as the **quorum controller/leader**.
- Significantly simplified architecture.

## Performance Gains
KRaft delivers substantially better:
- Controller shutdown time
- Recovery time after uncontrolled shutdown

## Conclusion
KRaft is a major improvement that simplifies operations and improves scalability and performance. The course covers how to launch a Kafka cluster in KRaft mode.
